# TreeVision customer-data security

Source remediation is based on the attached “Anon RLS policy exposes all Supabase estimates” report (vulnerable commit 4517641; claimed fix 934ebf2) and the actual main branch cd1475d. The claimed security PR was not found in the connected repository. This change supersedes its incomplete authenticated-user-only proposal.

## Access contract

* Anonymous clients cannot read, insert, update or delete estimates through PostgREST. Public submission remains intentionally available through `save-estimate`, which accepts bounded contact and preliminary analysis fields, sets pending status itself and returns only the new UUID.
* Staff access requires a verified Supabase user **and** explicit membership in `public.staff_members`. Client metadata, signup, arbitrary authenticated accounts and the removed shared crew password never grant staff access. The allowlist starts empty; only the selected operator-provisioned account is added during deployment. Removing membership immediately removes RLS access, including with an unexpired JWT. Legacy CRM `clients` and `jobs` tables are also restricted to staff when present.
* `tree-photos` is private. Restrictive storage policies defeat old permissive policies; direct client uploads are blocked. Save uploads a validated JPEG/PNG/WebP under a random path using the server-side service role. Dashboard photos use staff-authenticated signing for five minutes, including conversion of legacy public URLs. No requirement for public customer/property photos was found. Previously copied/publicly cached images cannot be recalled by an RLS change.
* `send-quote` verifies the user and allowlist before reading customer records or calling email services. Approval identity comes from the verified user. Public `analyze` is intentionally retained; it accepts one bounded photo/prompt, fixes the model and token budget, and drops arbitrary paid API options. Secrets are held only in function environment variables.
* Public CORS is intentional for intake and grants no database access. Service-only atomic UTC daily budgets cap analysis at 20, saves at 100 and quote emails at 100 across all callers/isolates. Invalid requests fail before consumption. Budget/database failures deny intake. These are cost/abuse ceilings, not bot identity verification: an attacker can exhaust the shared allowance. An operator can review and change the explicit limits in a new migration. No IP-header-dependent security claims are made.
* The Cloudflare/D1 system is a separate deployed architecture. Its intentionally shared customer resume token is a 96-bit random capability. Estimate IDs and photo IDs alone no longer grant read or mutation access. Staff uses the server-held admin secret; browser photo loads transmit it in headers, never URLs. Customer photo capability URLs are no-store and no-referrer. Anyone with a deliberately shared resume link can access that customer's estimate/photos. API request logging that could record share links was removed. No Cloudflare deployment or D1 migration was executed during this work.

## One activation-time operation (pending; not performed)

Keep Supabase inactive now. After the owner explicitly authorizes reactivation/costs, keep public traffic disabled while completing this deployment operation:

1. Reactivate separately; the script deliberately cannot do this. Set the Management API access token and the UUID of an intentionally provisioned staff account privately in the operator environment. Existing `ANTHROPIC_API_KEY`, `RESEND_API_KEY`, `QUOTE_FROM_EMAIL` and company secrets must be configured server-side. Use a current Supabase CLI and a trusted checkout of this branch.
2. Run `node scripts/deploy-security.mjs`. It refuses paused/unhealthy projects, disables hosted self-service/anonymous signup (local `config.toml` alone does **not** change hosted Auth), applies pending idempotent migrations, provisions exactly the selected existing staff UUID, and deploys the three guarded functions. It does not run automatically in CI, restore the project, or create a paid project/branch. Database linking may require the privately supplied database password.
3. The migration additively reconciles canonical `customer_*` columns with legacy `client_*` deployments and backfills contact/identification fields without deleting data. It preserves historical statuses while checking new writes. The save handler uses these canonical fields. Validate anon denial, nonstaff denial, staff read/update, private photos, revoked membership, hosted signup rejection, and one controlled public submission. Paid analysis/email validation requires its own authorized budget.

The script fails on every unsuccessful step; it is safe to rerun migrations. It does not claim production access verification or automatic rollback. The deployment workflow runs the security regression checks before publishing the Worker. Merging/deploying the source PR activates website/Worker changes. A pushed PR alone does not alter production databases, Edge Functions or deployed web assets.

## Automated checks

CI exercises real Postgres RLS/grants locally using PGlite, repeat application against legacy policies, anonymous/arbitrary account denial, allowlist removal, private storage, protected allowlist/budget RPCs and global budget exhaustion. Deno checks all functions and tests streamed body limits, malformed JSON/photos, paid-option filtering, verified-user-plus-membership checks and limiter failure handling. Worker request tests cover unauthenticated/wrong-token reads, all customer mutations, private-photo denial and valid capability/staff access. The previously inconsistent Worker lockfile was refreshed, the vulnerable Hono dependency was updated, and npm audit reports no known Worker vulnerabilities. Browser scripts are parsed and checked for password bypasses/privileged secrets. No CI test contacts the paused production project.
